## 0. 仓库定位与边界

### 0.1 一句话定义

> `AtriumCppTools` 存放 **长期维护、独立进程运行、由 `Steward` 托管生命周期** 的 C++ 重型工具。

### 0.2 本仓库收纳什么

- 需要 C++ 的结构性理由（性能 / 依赖 / 稳定性 / 跨语言复用，判定标准见 §11）的重型工具
- 由 `Steward` 拉起、观测、关闭的独立可执行工具进程
- 工具之间共享的公共 C++ 库（`common/`）

### 0.3 本仓库不收纳什么

| 不收纳 | 应放置位置 |
| :-- | :-- |
| 只需脚本化完成的能力 | `AtriumPyTools` 脚本层 |
| 轻量 CLI、文本处理、AI 胶水 | `AtriumPyTools/tools/` |
| 一次性验证、原型代码 | `AtriumPyTools`（原型转正后按 §11 评估是否迁入） |
| `Steward` 宿主自身的功能 | `AtriumSteward` |
| 笔记内容、附件、索引产物 | `AtriumNote` / `Storage` |

### 0.4 与相邻仓库的关系

```text
AtriumSteward  ──调用（manifest + 协议）──▶  AtriumCppTools
     │                                            │
     │                                            │ 只读/读写内容
     └───────── 只读（禁止引用其源码）              ▼
                                              AtriumNote / Storage
```

红线：`AtriumCppTools` **不得** `#include` 或链接 `AtriumSteward` 的任何源码；两者只通过 §5 契约交互。

## 1. 分支规范

### 1.1 当前生效分支布局

- `main`：主分支，`develop` + `tools` 的汇总，只做合入，不直接开发。
- `develop`：框架开发分支，承载 `common/`、构建系统、契约基线。
- `dev/basic`：框架开发分支，合入 `develop`。
- `tools`：工具汇总分支，所有工具合入本分支。
- `tool/<kebab-case>`：具体工具开发分支，合入 `tools`。

> **为什么工具分支是 `tool/` 而不是 `tools/`**（v2.2 修正）：git 无法同时存在 `refs/heads/tools` 与 `refs/heads/tools/<x>`——前者是一个文件，后者要求它是目录。实测（git 2.55.0）：
>
> ```
> $ git branch tools            # 成功
> $ git branch tools/loomery
> fatal: cannot lock ref 'refs/heads/tools/loomery':
>        'refs/heads/tools' exists; cannot create 'refs/heads/tools/loomery'
> ```
>
> 这是 git ref 存储模型的硬约束，无法绕过（红线 C18）。v1.x 的 §1.1 同时定义了 `tools` 与 `tools/xxx`，**该条文不可实施**。
>
> **派生链**：`develop` →（建立）`tools` →（建立）`tool/<tool>`。工具分支从 `tools` 派生，因此天然包含 `common/`，可独立构建；框架升级按 §1.2 第 5 条显式同步。

### 1.2 框架与工具的隔离模型（已确认）

**决策**：`tools/*` 只合入 `tools`，**不合入 `develop`**。框架（`develop`）与工具（`tools`）保持隔离。

这个模型是有效的，但必须配一组纪律，否则会退化成"框架无法反哺 + 分支永久漂移"。以下规则是对该模型的补充，不是替代：

1. **框架改动一律走 `develop`**。任何 `common/`、CMake、`CMakePresets.json`、构建脚本、契约文档的改动，都必须在 `develop` 上完成并合入 `dev/basic`，禁止在工具分支上改框架。
2. **禁止在工具分支上"就地打补丁修框架"**。发现框架缺陷时，正确路径是 `develop` 修复 → 工具分支同步；若框架修复尚未合入，工具分支应等待，而不是各自临时绕过。
3. **禁止把框架源码复制进工具分支**以绕开依赖——这会把一次修复变成多份副本，是隔离模型最容易退化的路径。
4. **每个工具分支必须记录兼容基线**：在 `Docs/ARCHITECTURE_DESIGN.md` 中记录其 `common/` 兼容基线（commit SHA 或版本号），格式统一，便于宿主与 CI 校验。
5. **框架升级是显式同步动作**：工具分支升级兼容基线的唯一方式是显式 merge/rebase 并更新基线记录，不得靠自动合并静默漂移。
6. **边界判定**：`common/`、顶层 CMake、presets、构建脚本、契约文档属于**框架**；`tools/<ToolName>/` 下的一切属于**工具**。一旦两个工具都需要同一段代码，该代码必须下沉到 `common/`，禁止互相复制。
7. **工具注册是自动的，工具分支永远不改框架文件**：`tools/CMakeLists.txt` 以自动发现方式遍历其直属子目录（含 `CMakeLists.txt` 者即视为一个工具）。因此**新增工具只需把自己的目录放进分支**，不必回到 `develop` 改注册表；多个工具分支合入 `tools` 时也不会在注册文件上冲突。这条同时消掉了此前"`tools/CMakeLists.txt` 算框架还是工具"的归属争议——它是框架文件，且不需要被工具分支修改。

代价说明（明示，避免误读）：此模型下框架改进**不会**自动流入未同步的工具分支。这是有意接受的成本，由上述第 4、5 条控制，而不是靠"到时候再说"。

### 1.3 分支操作规则

1. 禁止在 `main` 上直接提交。
2. 每个 `tools/<tool-id>` 分支必须包含所开发工具的 `README.md`；分支根目录保留仓库级 `README.md`（本文件）。
3. 每个工具目录必须包含 `Docs/`，其中至少有 `ARCHITECTURE_DESIGN.md`（模板见 §6.2）与 `README.md`（模板见 §6.1）。
4. 分支命名、工具目录名、`tool_id` 三者必须一致（见 §4.1）。
5. 删除分支前确认其内容已合入 `tools`。
6. 工具分支不得改动 `common/`、顶层 CMake 与 presets（见 §1.2 第 1 条）。

## 2. 设计原则

### 2.1 基本原则

1. **工具即进程**：每个工具是独立可执行文件，测试期禁止依赖编译期链接宿主。
2. **契约先行**：接入 `Steward` 前先定义 manifest 与协议，不写任何宿主调用代码。
3. **宿主零耦合**：工具在**没有** `Steward` 的情况下也必须能独立启动运行（见 §7.2）。
4. **能力先验证，语言后决定**：C++ 是手段而非身份，未通过 §11 评估的候选需求不进入本仓库。
5. **内容与代码分离**：工具读写 `AtriumNote` / `Storage`，但代码不与其混放。
6. **构建可复现**：任何人 clone 后按 `Docs/BUILD.md` 能一步产出同构可执行文件。
7. **产物不入库**：构建输出、依赖缓存、临时文件一律不进 Git。
8. **工具是完整产品**（已确认）：本仓库的每一个工具都必须是**可独立运行、功能完整**的应用。`Steward` 只负责**生命周期控制**——拉起、观测、关闭——**不承载工具的具体运行内容**（不托管其窗口、不代管其状态、不代跑其业务）。禁止设计任何"只有被 `Steward` 拉起才有意义"的工具。这是本仓库与宿主之间最根本的边界，也是 §7.2 的更严格表述。

### 2.2 与既有项目的能力复用边界（已确认）

`Projects/NexusRenderer`、`Projects/ChromaCMS` 与本仓库同属一个工作区，但**它们是独立项目，不依赖本仓库**，本仓库也不反向依赖它们。跨项目只允许以下三种关系：

| 关系 | 允许 | 说明 |
| :-- | :-- | :-- |
| 参考 | ✅ | 参考其架构决策与踩坑结论（如 ChromaCMS §2.6 的 Qt 原生视口路径、NexusRenderer 的红线 CI 化做法） |
| 搬运 | ✅ | 把某段能力**复制**进本仓库后在 `common/` 或工具内独立演化，必须记录来源 |
| 依赖 | ❌ | 不得让 `common/` 或工具 `link` / `#include` 那两个项目的 target 或源码 |

**红线：任何情况下都不允许把跨工作区的项目变成构建期依赖**——那会让 `AtriumCppTools` 的构建被 `Projects/` 的工程进度绑架，并违反工作区 v4 的 `Manager/` 与 `Projects/` 物理隔离原则。

#### 2.2.1 共享契约，不共享实现

复用既有能力时的唯一正确形态是**窄接口 + 各自实现**，而不是共享一个庞大的第三方依赖。接口放在哪里，取决于它有几个消费者（§2.3）：

```text
状态 A：只有一个消费者（当前）
  tools/<Tool>/
    contracts/media/IVideoSource.hpp  ← 窄接口 + POD，零第三方头文件
    src/media/FfmpegVideoSource.cpp   ← 唯一实现，第三方头文件只出现在这一层
    src/pdf/PdfiumDocument.cpp

状态 B：出现第二个消费者之后，接口才提升为共享契约
  common/media/IVideoSource.hpp       ← 只上移"接口 + POD"，实现不动
        ▲                    ▲
        │                    │
  tools/A/src/media/...   tools/B/src/media/...   ← 实现仍各自独立、各自演化
```

**注意状态 A 与状态 B 的区别**：v1.3 曾把"接口先放进 `common/`、实现留在工具内"当作默认做法，这条已被 §2.3 收紧——没有消费者的接口不进 `common/`。

理由（来自 ChromaCMS 的实践经验）：它的架构红线 8 规定 `libav*.h` 只允许出现在 `Runtime/Media/VideoLoader/` 内部。若把"带实现的解码库"提进 `common/`，所有工具都会被迫吃下 FFmpeg 的体积、许可与升级风险。**换后端只应改一个 `.cpp`。**

#### 2.2.2 拒绝重复实现（明确不作为）

`Loomery` **不自行实现**以下三类能力：

| 能力 | 现成实现 | 本仓库的正确做法 |
| :-- | :-- | :-- |
| **图渲染（Mermaid）** | 上游 `mermaid`（JS）；原生实现 `merman`、`mermaid-rs-renderer`（Rust） | **调用**其中之一，不自己写解析 / 布局 / 绘制 |
| 视频解码 | ChromaCMS 已选定 FFmpeg | §2.2.1 的窄接口 + 工具内实现 |
| PDF 渲染 | pdfium 等成熟库 | 同上 |

**关于图渲染（v2.0 新增，依据 §12.1.3 实测）**：Mermaid 有 35 种图型，自行实现等于重造一个上游项目。原生路线（`merman`）与浏览器路线（上游 `mermaid`）都是**使用**现成实现，**都符合本条**；**只有"用 C++ 自己写 Mermaid 渲染器"违反本条**。

这条必须写清楚，因为"图渲染"看起来像是笔记工具的核心能力，很容易被当成值得自研的部分。它不是——它是**依赖**。

至于视频与 PDF：视频播放需要 GPU 呈现路径，而笔记工具的骨架是图布局与文本排版，两套依赖面与复杂度完全不同；笔记工具的职责是**承载**媒体节点，不是成为 ChromaCMS 的低配复制品。

因此，§12.2 中候选的"媒体/PDF 索引器"**不作为并列的第二个工具**；它的正确形态是 §2.2.1 的接口层，实现按需落在实际使用的工具内。

### 2.3 `common/` 的准入条件

`common/` 与"工具内部的 `Runtime/` 层"唯一区别是：**`common/` 有第二个消费者**。只有一个消费者时，它退化成工具内部的层，却要额外付出接口冻结与版本锁定成本。因此：

1. 新代码进入 `common/` 前必须回答：**它现在有几个消费者？** 少于两个则**不放**——**包括"只放接口"**。
2. **"先定接口、实现留在工具内"不等于"接口可以先进 `common/`"。** 没有消费者的接口，却要所有工具分支承担它的兼容性维护成本，而且极易把尚未定案的决策**写死在公共头文件的注释里**（见下方修订记录，这正是真实发生过的事）。接口必须与真实实现、第二个消费者**同时**进入 `common/`。
3. 仓库骨架现在就建立 `common/` 与 `tools/` 两级目录（否则第二个工具落地时需大规模搬迁）。
4. `common/` 当前准入清单（每项均有 ≥2 个消费者的现实或已立项依据）：

| 模块 | 内容 | 消费者 |
| :-- | :-- | :-- |
| `text/` | `Utf8` / `Utf8View` | 全部工具 |
| `error/` | `ExitCode` / `ErrorKind` / `Error` / `Outcome<T>` | 全部工具 + 宿主协议 |
| `log/` | `LogLevel` / `ILogSink` / `Log()` | 全部工具 |
| `paths/` | 可执行文件与资源路径、环境变量读取 | 全部工具 |
| `platform/` | `NativeWindowHandle` 等基础 POD | 全部工具 |

**修订记录（v2.0）**：v1.3 曾在 `common/` 中预埋 `media/`（色彩标记 POD、视频/PDF 窄接口）与 `block/`（块模型），理由是"为第 4 档媒体深度预留"。按本条新措辞，**二者消费者均为零**；更糟的是 `block/BlockTypes.hpp` 的头部注释逐字写死了当时"块为唯一真源、Markdown 仅为导入导出"的决策——而该决策在 v2.0 已被推翻（§12.1.2）。二者已从 `common/` 移除：媒体接口待真实消费者出现时**连实现一并**进入；块模型则根本不再存在——Markdown 是唯一真源，块 / 索引只是工具内部的派生缓存（§12.1.2）。

## 3. 目录规范

### 3.1 仓库目标结构

```text
AtriumCppTools/
├── README.md                    # 本文件：仓库级规范
├── AGENTS.md                    # Agent 协作入口（工作区规范 §1.1 要求）
├── CMakeLists.txt               # 顶层工程
├── CMakePresets.json            # 构建预设（对齐 ChromaCMS 基线）
├── .gitignore
├── .gitattributes                # 统一换行与文本属性
├── .clang-format                 # 代码风格
├── build.bat                     # 构建入口脚本
├── common/                       # 工具间共享（无 UI、无业务，见 §2.3 准入条件）
│   ├── CMakeLists.txt
│   ├── include/atrium/common/
│   │   ├── text/                 #   UTF-8 文本类型
│   │   ├── error/                #   错误模型与 Outcome
│   │   ├── log/                  #   日志门面
│   │   ├── paths/                #   路径解析（禁止依赖进程 CWD）
│   │   └── platform/             #   基础 POD：窗口句柄等
│   ├── src/
│   └── tests/                    #   契约测试
├── tools/
│   └── <ToolName>/
│       ├── CMakeLists.txt
│       ├── include/<tool>/
│       ├── src/
│       ├── resources/
│       ├── tests/
│       ├── benchmarks/
│       ├── Docs/
│       │   ├── ARCHITECTURE_DESIGN.md
│       │   └── BUILD.md
│       └── README.md
├── third_party/                  # 第三方依赖（版本锁定，禁止改源）
├── docs/                         # 仓库级文档（构建、发布、契约同步）
└── launchers/                     # 仅本地调试用的单工具启动脚本
```

> **注意**：`docs/` 与工具内 `Docs/` 的大小写需在工作区内统一。当前 `AtriumSteward` 用 `Docs`，`AtriumPyTools` 用 `docs`，本仓库尚未建立。**建议全工作区统一为 `Docs/`**（待确认）。

### 3.2 目录红线

| 编号 | 规则 |
| :-- | :-- |
| D1 | `common/` 不得依赖任何 `tools/` 下的代码，依赖方向单向：`tools → common` |
| D2 | `common/` 不得包含 UI 框架依赖与具体工具业务逻辑 |
| D3 | 每个工具一个独立 CMake target，禁止工具之间直接 link 彼此 |
| D4 | 工具目录自包含：删除任一工具目录后其余工具仍可独立构建 |
| D5 | `third_party/` 源码禁止直接修改，需定制时迁移到工程自有目录 |
| D6 | 构建产物只出现在 `build/`，且 `build/` 必须被忽略 |
| D7 | `common/` 不得 `link` 或 `#include` `Projects/` 下任何项目（§2.2） |
| D8 | 第三方实现与资源（解码库、图渲染后端、`mermaid.min.js` 等 JS 资源）只允许出现在 `third_party/` 或工具内的具体实现目录；**不得进入 `common/`**（§2.3） |
| D9 | 工具名**不带** `Atrium` 前缀；`namespace atrium` 指工作区家族，两者无关（§4.3） |

## 4. 命名与标识规范

### 4.1 三元一致原则

同一个工具在以下三处必须使用**同一个**标识：

| 位置 | 形式 | 示例 |
| :-- | :-- | :-- |
| 仓库目录 | `PascalCase` | `Loomery/` |
| Git 分支 | `tool/<kebab-case>` | `tool/loomery` |
| `tool_id`（manifest / Steward 注册表） | `kebab-case` | `loomery` |

### 4.2 可执行文件命名

- 产物名统一为 `kebab-case`，与 `tool_id` 一致：`loomery.exe`
- 禁止使用空格、中文、大小写混排作为产物名
- 调试与发布产物同名，仅以构建目录区分

### 4.3 工具名命名规范

工具名 = **一个单义名词，不加 `Atrium` 前缀**。

| 规则 | 说明 |
| :-- | :-- |
| **不加 `Atrium` 前缀** | 前缀属于**工作区家族**（`AtriumSteward` / `AtriumPyTools` / `AtriumCppTools`），不属于单个工具。`AtriumPyTools` 下的工具本来就是 `colorpicker` / `filechecker`，本仓库与之对齐 |
| 禁止形态词 | 不带 `Canvas` / `App` / `Tool` / `Editor` / `Studio`——形态会变，名字不该承载形态 |
| 禁止与仓库角色撞名 | 不得用 `Note`（内容仓库为 `AtriumNote`），不得用语言标记（`Py` / `Cpp`） |
| 必须单义 | 名字应指向**能力**而非实现手段；同时能被一句话解释 |
| 长度 | 建议 ≤ 16 字符，因为要同时派生目录名、分支名、`tool_id`、管道名 |
| 名称冲突 | 定名前必须检索一次，避开同领域知名产品名——重名会在搜索、分发、包管理上持续撞车 |
| 名不符实是缺陷 | 名字暗示了不具备的能力（如叫 `Canvas` 却不支持自由摆放）会持续误导实现方向，按文档缺陷处理 |

**命名决策记录**：首个工具 `AtriumCanvasNote` → `AtriumLoom` → **`Loomery`**（v2.0）。

1. `AtriumCanvasNote`：`Note` 与内容仓库 `AtriumNote` 撞名，与 v5 §2.5"应用与内容必须分离"的意图冲突；`Canvas` 暗示自由画布，而定位本质是图不是画布。
2. `AtriumLoom`（决策 D-2 / D-10）：隐喻正确——把文字、图、引用**织**在一起；但 `Atrium` 前缀与 `AtriumPyTools` 的既有实践不一致。
3. **`Loomery`**（织造工坊，`loom` 的派生词）：保留 loom 词根与"织"的隐喻；避开 `Loom`（Loom.com 录屏工具，同领域重名）与 `Atlas`（MongoDB Atlas 等大量撞名）；无 `Atrium` 前缀。

> **`namespace atrium` 不随工具名变化**：`atrium::common` 里的 `atrium` 指**工作区家族**，与"工具名不加前缀"是两件事。去掉工具名前缀**不影响** `namespace atrium`。

## 5. Steward 生命周期契约（核心）

> 本节是本仓库存在的理由。任何工具在接入 `Steward` 前，必须先满足本节全部条目。

### 5.1 契约原则

1. `Steward` 只通过 **manifest + 协议** 调用工具，禁止源码直连（依据 v5 红线 `V5-S4`）。
2. **生命周期归宿主**：`Steward` 决定工具的启动、停止与重启；**状态归工具**：工具自己实现业务状态机。
3. **渐进增强**：manifest 出现未知字段时，`Steward` 必须忽略而非报错；协议版本不匹配时，工具必须拒绝服务并给出明确退出码，而不是降级静默运行。
4. **单向依赖**：工具可以读取 `Steward` 传入的上下文，禁止工具反向调用 `Steward` 内部接口。

### 5.2 工具清单：`tool.manifest.json`

每个工具必须在 `Docs/` 下提供 manifest，字段最小集：

| 字段 | 必填 | 说明 |
| :-- | :-- | :-- |
| `schema_version` | 是 | manifest 结构版本，整数 |
| `tool_id` | 是 | 与 §4.1 一致 |
| `title` | 是 | 面板显示名 |
| `version` | 是 | 语义化版本 `MAJOR.MINOR.PATCH` |
| `entry` | 是 | 可执行文件相对路径（相对构建产物根） |
| `args` | 否 | 宿主启动时附加的固定参数 |
| `transport` | 是 | 当前固定为 `named-pipe`（见 §5.4.2） |
| `protocol_version` | 是 | 协议版本，整数 |
| `singleton` | 是 | 是否只允许一个实例 |
| `requires` | 否 | 运行前提（如 `storage`、`atrium-note`、指定字体） |
| `capabilities` | 否 | 能力声明，供宿主做入口展示与调度 |
| `perf_budget` | 否 | 与 §8.3 对齐的启动/内存预算，供宿主做超时判定 |

**待确认**：字段命名与 `AtriumContracts/`（v5 §9 规划）的落地形式，需与 `AtriumSteward` 同步后冻结。`AtriumContracts/` 目录当前尚未创建，本期以本文件 §5.4.2 与协议文档为权威来源。

### 5.3 通信通道原则

- 通道只允许**本机**使用，禁止对公网监听。
- 通道必须支持**双向**：宿主下发命令、工具上报状态。
- 禁止：共享内存直接改宿主状态、工具写宿主配置文件、工具注册全局钩子后不注销。
- 具体通道选型见 §5.4.2。

### 5.4 消息格式

所有消息统一信封，禁止裸文本协议：

| 字段 | 说明 |
| :-- | :-- |
| `protocol_version` | 与 manifest 一致 |
| `type` | 消息类型（见 §5.5、§5.6） |
| `id` | 请求 ID，响应必须回填同值 |
| `ts` | 时间戳（UTC，毫秒） |
| `payload` | 类型相关负载 |

编码统一 UTF-8。

#### 5.4.1 帧格式（二进制，禁止裸文本协议）

在通道之上使用**长度前缀 + JSON 载荷**：

```text
+----------------+---------------------------+
| uint32 LE len  |  len 字节 UTF-8 JSON 载荷  |
+----------------+---------------------------+
```

规则：

1. `len` 为该帧载荷的字节数，不含自身 4 字节，小端无符号 32 位。
2. 载荷必须是 UTF-8 编码的 JSON 对象，且必须包含本节列出的信封字段。
3. 单帧载荷上限 **1 MiB**；超过上限的行为是**拒绝并断开连接**，不得截断后继续。
4. 禁止使用换行分隔 JSON（NDJSON）作为帧格式；禁止依赖"读到 EOF 才算一帧"。
5. 不允许"只发长度不发载荷"或半帧发送；发送端必须一次写完整帧。

**信封字段**（载荷内的固定字段）：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `protocol_version` | int | 与 manifest 及协议文档一致 |
| `type` | string | 消息类型，取值见 §5.5 / §5.6 |
| `id` | string | 请求 ID；响应必须回填同值 |
| `ts` | int | UTC 毫秒时间戳 |
| `payload` | object | 类型相关负载，可为空对象 |

- 字段名与枚举值统一 `snake_case` 小写。
- 时间戳统一 UTC 毫秒整数，禁止本地时间与字符串时间。
- 出现未知 `type` 时，接收方必须忽略并记录，不得崩溃、不得断开连接（向前兼容）。

#### 5.4.2 传输通道：Windows 命名管道（已确认）

**决策**：本机 **Windows 原生命名管道（Named Pipe）**，不使用回环 TCP，不使用公网监听。

| 项 | 约定 |
| :-- | :-- |
| 路径 | `\\.\pipe\atrium.steward.<tool_id>`，`<tool_id>` 内不得出现路径分隔符 |
| 命名空间 | 只允许用户级命名空间；**禁止** `\\.\pipe\global\` 前缀 |
| 角色 | **工具是服务端**（创建并监听管道实例），**宿主是客户端**（连接） |
| 连接数 | 同一时刻只接受**一个**有效连接；多余连接直接拒绝，不进入命令循环 |
| 权限 | 默认仅允许当前用户访问；如需放宽必须在架构文档中说明理由 |
| 消息模式 | **字节模式（byte mode）**；禁止消息模式（message mode），避免 MTU 相关的分片语义差异 |
| 实例数 | 首个实例成功创建即代表本工具已就绪；工具在收到 `shutdown` 前不得主动关闭监听 |
| 清理 | 进程退出后管道自动消失；但必须处理"上一次异常退出残留监听"的场景（重试 + 超时后返回退出码 4） |

**单实例由传输层天然保证**：当 `singleton = true` 时，工具以"创建管道名为 `<tool_id>` 的首个实例"作为抢占；创建失败即说明已有实例在运行，此时工具必须向该实例发起一次唤醒通知后以**退出码 4** 退出，不得静默抢占，也不得依赖 `.lock` 文件或进程名枚举。

**就绪顺序**：工具必须**先创建管道监听，再上报 `ready`**；反之宿主会连接失败。

**跨平台说明**：命名管道为 Windows 专有实现。macOS 侧需等价实现（`AF_UNIX` 域套接字或 `FIFO`），该差异必须在工具的架构文档中显式声明；本仓库当前主力平台为 Windows x64。


### 5.5 宿主 → 工具（命令）

| 命令 | 语义 | 要求 |
| :-- | :-- | :-- |
| `context.update` | 同步工作区上下文（当前项目、笔记库、任务） | 幂等，可随时到达 |
| `activate` | 唤起窗口 / 置前 | 幂等 |
| `deactivate` | 隐藏 / 让出焦点 | 幂等 |
| `ping` | 健康检查 | 必须应答 |
| `shutdown` | 优雅退出 | 见 §5.7 |

### 5.6 工具 → 宿主（上报）

| 类型 | 语义 | 要求 |
| :-- | :-- | :-- |
| `ready` | 初始化完成，可以接命令 | 启动后必须上报一次，且只上报一次 |
| `heartbeat` | 存活心跳 | 周期固定，写入 manifest |
| `status` | 业务状态（空闲/忙碌/错误） | 状态变化时上报 |
| `error` | 错误报告 | 附错误码与可读描述 |
| `log` | 结构化日志 | 禁止用 stdout 充当协议通道 |
| `exit` | 主动退出通知 | 附退出码与原因 |

### 5.7 生命周期时序（强制）

```text
Steward                          Tool
   │  spawn(entry, args, env)      │
   │──────────────────────────────▶│
   │                               │ 初始化（不阻塞 UI 线程）
   │            ready ◀────────────│
   │◀──────────heartbeat──────────▶│ 周期心跳
   │  context.update ─────────────▶│
   │  activate ───────────────────▶│
   │                               │
   │  shutdown ───────────────────▶│
   │                               │ 落盘、释放资源、注销钩子
   │            exit(0) ◀──────────│
   │                               ✂ 进程结束
```

必须满足：

1. **启动预算**：从 `spawn` 到 `ready` 的耗时不得超过 manifest 声明的预算；超时视为启动失败。
2. **优雅退出**：收到 `shutdown` 后必须在预算内自行退出并返回 `0`。
3. **强制回收**：宿主超时后会 `terminate` 再 `kill`，工具不得依赖"宿主一定会等我"。
4. **无孤儿**：工具不得启动未被 manifest 声明的子进程；如必须启动，需声明并在退出时一并回收。
5. **单实例**：当 `singleton = true` 时，重复启动必须快速退出（非零退出码 + 明确提示），不得静默抢占。
6. **崩溃可诊断**：异常退出前尽量写入崩溃日志与退出码，便于宿主归类故障。

### 5.8 退出码约定

| 退出码 | 含义 |
| :-- | :-- |
| `0` | 正常退出（含响应 `shutdown`） |
| `1` | 运行期失败 |
| `2` | 启动前置条件不满足（缺依赖、路径不可用） |
| `3` | 协议版本或 manifest 不兼容 |
| `4` | 单实例冲突 |

### 5.9 上下文与配置

- 宿主通过启动参数 / 环境变量 / `context.update` 传入上下文，工具**不得**自行猜测工作区路径。
- 配置优先级：`manifest 默认值 < 工作区配置 < 用户配置 < 命令行参数`。
- 配置文件与日志编码统一 UTF-8。
- 状态类数据只允许写入 `Storage/cache/<tool_id>/`，不得写入自身仓库目录（保证工作树干净）。

### 5.10 契约版本管理

- 协议变更必须升 `protocol_version`，并在 `CHANGELOG.md` 记录破坏性变更。
- 宿主与工具至少支持"当前版本 + 上一版本"兼容读取。
- 契约变更必须同步 `AtriumSteward` 侧适配层，不允许单边先行。

## 7. 接口与进程规范

### 7.1 CLI 参数（除协议外的第二条稳定接口）

- 必须支持 `--help`、`--version`
- 必须支持 `--no-steward`（或等价开关）用于脱离宿主独立调试
- 参数解析失败时返回退出码 `2`，并输出可读原因
- 禁止在参数名上使用宿主实现细节（如窗口类名）

### 7.2 独立可运行原则

工具必须在**没有安装 / 没有运行** `Steward` 的环境下独立启动并完成**全部功能**——是"完整产品"，不是"完整产品的降级版"。违规设计直接否决，这是防止宿主膨胀（v5 §2.2）与保证可测试性的底线。

推论（已确认）：

| # | 要求 | 反例（禁止） |
| :-- | :-- | :-- |
| 1 | 所有功能在无 `Steward` 时可用 | "查看笔记库概览需要 Steward 提供上下文" |
| 2 | 不要求额外加强，但也不允许削减 | "脱离 Steward 时只能只读打开" |
| 3 | `Steward` 不托管工具窗口、不代管工具状态、不代跑工具业务 | 工具把视图状态寄存在宿主进程 |
| 4 | 工具的本地配置与状态必须自洽于自身 | 配置只能从宿主下发 |
| 5 | 接入 `Steward` 只是**增量能力**（可被唤醒、可被观测、可被统一关闭） | 接入后功能变多、不接入则功能缺失 |

### 7.3 语言与工程标准

- 语言标准：**C++20**（与 `NexusRenderer` / `ChromaCMS` 基线对齐；如需 C++23 需在架构文档说明理由）
- 编译器：MSVC x64（主力），允许 MinGW/Clang 作为交叉验证；平台差异必须在架构文档中声明
- 构建：CMake + `CMakePresets.json`，预设命名沿用 `windows-ninja-debug` / `windows-vs2026-debug` 形态
- 依赖：优先系统依赖与 header-only；引入重型第三方库必须在架构文档中记录理由与体积代价
- 线程与异步：UI 线程禁止阻塞 IO；长任务必须有取消路径
- 内存与资源：RAII 为默认；禁止裸 `new/delete`；跨 DLL 边界不得传递 STL 对象所有权（除非 ABI 明确约定）

### 7.4 编码与文本

- 所有文本文件统一 UTF-8（无 BOM），换行按 `.gitattributes` 归一
- 禁止在源码与文档中提交乱码文本（当前 `AtriumSteward/.trae/rules/git-commit-message.md`、`AtriumPyTools/pyproject.toml` 均为反例，应在各自仓库修复）

### 7.5 稳定性分级

工具必须在 manifest 中声明稳定性等级，宿主据此决定是否默认启用：

| 等级 | 含义 | 宿主行为 |
| :-- | :-- | :-- |
| `experimental` | 接口可能变 | 默认隐藏，手动开启 |
| `beta` | 功能可用，契约稳定 | 默认展示，标注 |
| `stable` | 生产可用 | 默认启用 |

## 8. 构建、依赖与产物规范

### 8.1 构建

- 顶层 `CMakeLists.txt` 只负责聚合与全局设置，工具业务逻辑不写在这里
- 每个工具独立 target，可单独构建：`cmake --build build --target <tool>`
- 构建产物统一输出到 `build/<preset>/bin/`，禁止散落到源码目录
- 必须提供一键脚本（`build.bat`）与 `Docs/BUILD.md`

### 8.2 依赖管理

- 第三方依赖版本必须**锁定**（固定 commit / tag），禁止跟随分支
- 优先复用工作区已有依赖，避免同类库重复引入（例如矩阵库、图像解码库各只允许一套）

## 11. 新工具准入评估（立项前必答）

任何候选工具在写入分支前，必须回答以下问题；**任一题不满足即不进入本仓库**。

1. **形态**：它是脚本、CLI 工具，还是常驻/交互应用？（只有后两类才有资格讨论 C++）
2. **瓶颈**：Python 的瓶颈是"内存/CPU/延迟/第三方库缺失"中的哪一个？给出量化证据（延迟目标、数据规模、帧率）。
3. **加速层方案**：能否用"Python 主管 + C++ 扩展模块"解决？若能，则**不新建**独立工具项目，改写 `AtriumPyTools`。
4. **依赖**：所需核心依赖（解码器、渲染器、GUI 框架）在 Python 生态是否确实不可用或不稳定？
5. **预算**：启动时间、内存、帧率、延迟目标是多少？超了会怎样？
6. **宿主关系**：它如何被 `Steward` 管理？准备提供哪些命令与上报？
7. **长期性**：预期维护 3 年以上吗？一年后还会用吗？
8. **落位**：是否与 `AtriumPyTools`、`AtriumSteward`、`Projects/` 已有能力重复？
9. **界面层归属**：界面用原生控件还是 web 渲染（如 WebView2）？若为 web 渲染，必须明确说明**为何仍值得用 C++ 承载**（全库索引、文件 IO、启动延迟、内存、被 `Steward` 托管的原生进程）——因为此时大部分产品价值落在 HTML/JS 侧。本题不需要"通过"，但**必须显式回答**，不允许默认滑过去。

**评估结论只有三种**，不得出现"先做做看"：

| 结论 | 处理 |
| :-- | :-- |
| 脚本即可 | 进 `AtriumPyTools` 脚本层，本仓库不受理 |
| Python 主管 + C++ 扩展 | 改造 `AtriumPyTools` 对应工具，本仓库不受理 |
| 独立 C++ 工具 | 在本仓库建分支，且必须同时产出 §12.1.1 级别的量化预算 |

#### 12.1.2 核心定位：Markdown 文件为唯一真源（推翻 v1.3 的 D-11）

| 维度 | 决策 |
| :-- | :-- |
| **唯一真源** | **磁盘上的 Markdown 文件本身**。它人类可读、可被任意编辑器打开、可被 git 直接版本化 |
| **索引的角色** | 解析产生的块 / 段落结构是**派生物、可随时重建的缓存**，不是真源。删掉索引后从 Markdown 全量重建，语义必须完全一致 |
| **视图** | 文档（阅读为主）/ 图（笔记间的引用关系）；二者是同一份 Markdown 的不同呈现。数据库视图降为待评估（Q10） |
| **Mermaid 的角色** | Markdown 围栏代码块 ` ```mermaid ` 里的内容，交由渲染器画成图。**它是内容的一部分，不是独立存储格式** |
| **规模含义** | 以**文件数与总字节数**衡量，不以"块数"衡量（见 §12.1.1 校准依据） |

**为什么改回来**：v1.3 的 D-11 选择"块存储为唯一真源、Markdown 降为导入导出"，路线是自研 Notion 级块编辑器。v2.0 收窄为"Markdown 阅读器 + 内嵌 Mermaid 可视化"，理由：

1. **真源必须是最不易丢失的形态。** Markdown 可被任何工具读写、被 git 直接 diff；自有块格式一旦损坏或工具停更，全库内容就成了需要专门工具才能读出的孤岛。在个人笔记场景里，这个风险远大于块模型带来的表达能力收益。
2. **块模型的成本主要在编辑器，不在阅读器。** 富块编辑（拖拽、嵌套、协同、增量持久化）是 Notion 级复杂度；一个以阅读为主、辅以 Mermaid 可视化的工具不需要它。
3. **与 v5 一致，不再需要修订上位文档。** v5 §8.2 规定该工具"以 Markdown 为主存储格式"，§2.5 要求"内容仓库负责 Markdown 文件"。**本决策与 v5 一致**——v1.3 那份"必须同步修订 v5 §8.2/§2.5"的待办随之作废。

**保留的能力承诺**：Markdown 里已有的 `[[wiki 链接]]` 与相对路径链接仍要解析成图的边；图视图与全库检索仍是核心能力。它们建立在**重新解析 Markdown** 之上，不依赖任何自有块格式。

**被此决策推翻的部分**：v1.3 的 D-11、原 §12.1.2 全文、原 Q8/Q11 中关于"块格式归属"的表述、以及 `common/block/` 两个头文件（已删除，见 §2.3 修订记录）。

#### 12.1.1 量化预算（已定案）

**A 组：决策输入**

| # | 决策 | 结果 |
| :-- | :-- | :-- |
| A1 | 规模 | **全库 10,000 个 Markdown 文件可检索；单篇 ≤ 5,000 行；同屏渲染 ≤ 2,000 个块元素** |
| A2 | 手感优先级 | 启动时间与交互帧率**同等重要**，不做取舍，二者共享同一预算包 |
| A3 | 媒体深度 | **MVP 零媒体承载**（只有文档编辑与阅读）；未来目标为第 4 档（视频可播放 + PDF 可逐页阅读），接口按此预留 |
| A4 | 独立性 | 脱离 `Steward` 时**完成全部功能**（不加强、不削减）；`Steward` 只做生命周期控制 |

**A1 的量级校准依据**（为什么是 10,000 个文件）：

| 使用形态 | 文件数 | 总字节量级 |
| :-- | :-- | :-- |
| 个人轻中度 | 300 – 1,000 | 数 MB |
| **本项目目标（个人重度 / 长期全量迁移）** | **10,000** | 数十 MB |
| 团队级 | 50,000+ | 数百 MB |

**与 v1.3 的差别**：v1.3 以"块数"为关键指标（10 万块），那是**块编辑器**的度量。阅读器的真实压力来自两处——**文件数量**（扫描与索引成本）与**单篇的图数量**（渲染成本）。因此预算的着力点从"块树虚拟化 + 增量布局"转向"文件索引 + 图渲染"：

- < 1,000 文件：可全量载入 + 线性扫描，架构最简单。
- **≈ 10,000 文件（本项目）**：必须有本地全文索引；扫描必须增量（不全量重读）；图视图必须走索引而非全量解析。
- > 50,000 文件：需要更强的索引层与分页 / 流式；**本项目不追求该档位**。

**新引入的关键变量是"单篇的图数量"**：一篇笔记含 1 张图与含 20 张图，开页成本差一个数量级（单图热态渲染 12.9–29.9 ms，见 §12.1.3）。开页预算必须按"图数量 × 单图成本"核算，而不能只看字符数。

**B 组：由 A 组推导的预算（可测量、可验收）**

| 指标 | 基线 | 依据 |
| :-- | :-- | :-- |
| 冷启动到 `ready` | **≤ 1500 ms** | 含索引加载。**不含 WebView2 宿主创建成本——该成本尚未实测，是当前最大风险项**（§12.1.4） |
| 空闲常驻内存 | **≤ 400 MB** | 由 A1 反推：10,000 文件不可全量常驻 ⇒ 索引驻留 + 视口内内容。**含 WebView2 的 Chromium 子进程开销（未实测）** |

| 打开单篇延迟 | **≤ 150 ms** | 阅读手感；受"图数量"约束（见上方 A1 校准依据） |

#### 12.1.3 图渲染栈实测（v2.0 新增，已执行）

比较 `merman` v0.7.0（Rust，无浏览器）与上游 mermaid v11（Chromium），在同一台机器上实测：

| 维度 | `merman-cli`（原生路线） | 上游 `mermaid`（WebView2 路线） |
| :-- | :-- | :-- |
| 单图耗时（含进程启动） | 49 – 75 ms | — |
| 单图耗时（进程内热态） | — | **12.9 – 29.9 ms** |
| 保真度 | 与官方 `mmdc` 逐像素一致（第三方报告） | **即上游本身，100%** |
| SVG 可移植性 | ❌ 节点标签全在 `<foreignObject>`、`<text>` 为 **0** → QtSvg / librsvg / Inkscape 会画出**空框且退出码 0** | ❌ 上游自身也大量使用 `<foreignObject>`（3 图共 15 个） |
| 显示路径 | **只能走 PNG 位图**（已实测中文无裁切） | 浏览器内直接渲染：矢量、可缩放、图内文字可选 |
| 依赖面 | 单个 28.8 MB exe；做静态库链接则需引入 **Rust 工具链** | WebView2 运行时（Win10/11 自带）+ `mermaid.min.js` **3.49 MB** |
| Markdown 解析 | 需另配（`md4c` 等） | Chromium **不解析 Markdown**，同样需另配 |

**结论**：两条路线**渲染速度同量级**，差别不在性能，而在**保真度与显示质量**。原生路线被迫降级为 PNG 位图（失去矢量缩放与图内文字选择），且布局受 `merman` 与上游差异的约束；WebView2 路线拿到的是**上游本身**。因此选 WebView2。

**本实测推翻了两个先入为主的判断**，记录下来避免重复踩：

1. **「web 渲染太慢」不成立。** 某第三方对比报告中 `mmdc` 的 3.0 s **完全是每次新建浏览器的冷启动**，不是渲染耗时；热态渲染只要十几到三十毫秒。
2. **「原生 SVG 可移植」不成立。** 上游 mermaid 自己就大量使用 `<foreignObject>`，所以这不是某个实现的质量问题，而是 Mermaid 输出的固有形态——**任何"生成 SVG 再交给非浏览器渲染"的方案都会踩这个坑**。

**此外它还收窄了本工具的语言判断**：既然排版与图渲染都交给 Chromium，C++ 的价值退到**全库索引、文件 IO、启动延迟、内存控制、以及被 `Steward` 托管的原生进程**。这仍然值得用 C++（上万文件的检索与原生启动速度是 Python 做不到的），但 §0.1「C++ 重型工具」的表述应理解为"**核心用 C++**"，而不是"每一行都用 C++"。这一取舍已按 §11 第 9 题显式记录。

#### 12.1.4 待做的宿主成本实测（阻塞正式定案）

§12.1.3 只测了**渲染器**，没测**宿主**。以下三项必须用一个最小 C++ WebView2 宿主实测，因为它们直接决定 §5 生命周期契约是否成立：

| 待测项 | 为什么必须测 | 对应约束 |
| :-- | :-- | :-- |
| 冷启动（创建 environment → 首次导航完成） | WebView2 会拉起 `msedgewebview2.exe` 及子进程，最可能击穿 ≤1500 ms | §12.1.1 |
| 常驻内存 | Chromium 多进程通常加 80–250 MB | §12.1.1 的 ≤400 MB |
| **杀进程后是否残留 `msedgewebview2.exe`** | 未正确释放 environment 会留下孤儿进程 | **§9.3 明确禁止的行为**；§5 生命周期 |

第三项是选 WebView2 最大的集成风险，也是最容易漏掉的一项。它必须成为 shutdown 流程里的**显式步骤**和**一条测试用例**（Q13）。

### 12.2 待评估候选

| 候选 | 解决什么问题 | 语言初步判断 | 关注点 |
| :-- | :-- | :-- | :-- |
| ~~媒体/PDF 索引器~~ | 笔记附件与 PDF 的解析、缩略图、全文索引、OCR | — | **已否决为独立工具**（§2.2.2）：正确形态是 §2.2.1 的窄接口 + 工具内实现；解码能力已有 ChromaCMS 在做，重复实现无收益 |
| 视频/PDF 能力的外部化载体 | 把"取帧 / 渲染页"从消费者中解耦，供多个工具复用 | 取决于 A3；若需 GPU 呈现则复杂 | 可能是独立进程（由 Steward 托管）而非共享库；**仅在被第二个工具消费时才立项**（§2.3） |
| 实时文件系统监视服务 | 工作区变更感知、缓存失效、笔记增量索引 | 倾向 C++（`ReadDirectoryChangesW`），但需要证据 | 常驻成本 vs `Steward` 自带轻量轮询 |
| 大资产管道（纹理/压缩/格式转换） | `NexusRenderer`/`ChromaCMS` 的离线资产处理 | 需评估：若是批处理且调用已有工具链，则应留在 Python 编排 | 涉及跨工作区，优先留在各自项目内（§2.2 禁止构建期依赖） |
| 屏幕实时测量/色彩分析 | 高频（>60Hz）屏幕采样与色彩空间计算 | 优先"Python 主管 + C++ 扩展"（`colorpicker` 已规划此方案） | 不得新建独立项目；评估与 `colorpicker` 的边界 |
| 音视频合成/转码 | 录屏、剪辑合成 | 倾向调用外部工具链（ffmpeg）由 Python 编排 | 只有自研解码/实时渲染才考虑 C++ |

### 12.3 明确不建议进入本仓库

| 候选 | 原因 |
| :-- | :-- |
| 批量重命名、重复文件检测、目录清理 | 一次性/低负载脚本，`AtriumPyTools` 即可 |
| Markdown 预处理、AI 摘要、笔记批处理 | 文本处理与外部服务整合，Python 优势区间 |
| 任何"顺便用 C++ 重写一下"的 Python 工具 | 违反 §11 第 2、3 条；无量化收益的迁移是负债 |
