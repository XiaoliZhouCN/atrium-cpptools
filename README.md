# atrium-cpptools

> **定位**：`Manager` 工作区的 **C++ 重型工具仓库**。
> **上位依据**：`AtriumSteward/Docs/ARCHITECTURE_DESIGN.md`
> **工作区规范**：`AtriumSteward/Docs/WORKSPACE_SPECIFICATION.md`

---

## 0. 仓库定位与边界

### 0.1 一句话定义

> `AtriumCppTools` 存放 **长期维护、独立进程运行、由 `Steward` 托管生命周期** 的 C++ 重型工具。

### 0.2 本仓库收纳什么

- 需要 C++ 的结构性理由（性能 / 依赖 / 稳定性 / 跨语言复用，判定标准见 §8 新工具准入）的重型工具
- 由 `Steward` 拉起、观测、关闭的独立可执行工具进程
- 工具之间共享的公共 C++ 库（`common/`）

### 0.3 本仓库不收纳什么

| 不收纳 | 应放置位置 |
| :-- | :-- |
| 只需脚本化完成的能力 | `AtriumPyTools` 脚本层 |
| 轻量 CLI、文本处理、AI 胶水 | `AtriumPyTools/tools/` |
| 一次性验证、原型代码 | `AtriumPyTools`（原型转正后按 §8 评估是否迁入） |
| `Steward` 宿主自身的功能 | `AtriumSteward` |
| 笔记内容、附件、索引产物 | `AtriumNote` / `Storage` |

### 0.4 与相邻仓库的关系

```text
AtriumSteward  ──调用（manifest + 协议）──▶  AtriumCppTools
     │                                            │
     │                                            │ 只读/读写内容
     └───────── 只读（禁止引用其源码）              ▼
                                              AtriumNote / Storage
```

红线：`AtriumCppTools` **不得** `#include` 或链接 `AtriumSteward` 的任何源码；两者只通过契约交互。

## 1. 设计原则

完整论述见 [`docs/DESIGN_PRINCIPLES.md`](docs/DESIGN_PRINCIPLES.md)。核心八条：

1. **工具即进程**：每个工具是独立可执行文件，测试期禁止依赖编译期链接宿主。
2. **契约先行**：接入 `Steward` 前先定义 manifest 与协议，不写任何宿主调用代码。
3. **宿主零耦合**：工具在**没有** `Steward` 的情况下也必须能独立启动运行。
4. **能力先验证，语言后决定**：C++ 是手段而非身份，未通过准入评估的候选需求不进入本仓库。
5. **内容与代码分离**：工具读写 `AtriumNote` / `Storage`，但代码不与其混放。
6. **构建可复现**：任何人 clone 后按 `Docs/BUILD.md` 能一步产出同构可执行文件。
7. **产物不入库**：构建输出、依赖缓存、临时文件一律不进 Git。
8. **工具是完整产品**：`Steward` 只负责生命周期控制——拉起、观测、关闭——**不承载工具的具体运行内容**。禁止设计任何"只有被 `Steward` 拉起才有意义"的工具。

**跨项目复用边界**：`Projects/NexusRenderer`、`Projects/ChromaCMS` 与本仓库同属一个工作区，但互为独立项目。跨项目只允许「参考」（参考架构决策与踩坑结论）与「搬运」（复制进本仓库后独立演化，须记录来源）两种关系；**任何情况下都不允许把跨工作区的项目变成构建期依赖**。

**`common/` 准入条件**：必须有**第二个消费者**，且**接口本身也算**——没有消费者的接口不许进 `common/`。当前准入清单：`text` / `error` / `log` / `paths` / `platform`。

## 2. 分支模型

完整纪律见 [`docs/BRANCH_MODEL.md`](docs/BRANCH_MODEL.md)。要点：

- `main` 只做合入，不直接开发。
- `develop` / `dev/basic` 是框架分支，承载 `common/`、构建系统、契约基线。
- `tools` 是工具汇总分支；`tool/<kebab-case>` 是具体工具开发分支。
- 派生链 `develop` → `tools` → `tool/<tool>`；工具分支天然包含 `common/`，可独立构建。
- **框架改动只走 `develop`**；工具分支不得修改 `common/`、顶层 CMake 与 presets，也不得复制框架源码。
- 工具注册是**自动发现**的（`tools/CMakeLists.txt` 遍历直属子目录），新增工具不需要改任何框架文件。

> 工具分支前缀必须是 `tool/` 而非 `tools/`：git 无法同时存在 `refs/heads/tools` 与 `refs/heads/tools/<x>`（红线 C18）。

| 编号 | 规则 |

## 4. 命名

**三元一致**：同一个工具在仓库目录（`PascalCase`）、Git 分支（`tool/<kebab-case>`）、`tool_id`（`kebab-case`）三处必须一致。产物名 `kebab-case`，与 `tool_id` 相同。

**工具名 = 一个单义名词，不加 `Atrium` 前缀**，不带 `Canvas` / `App` / `Tool` / `Editor` / `Studio` 等形态词，不得与仓库角色撞名。

完整规范与命名决策记录见 [`docs/NAMING_AND_INTERFACES.md`](docs/NAMING_AND_INTERFACES.md)。

## 5. Steward 生命周期契约（核心）

> 本节是本仓库存在的理由。任何工具在接入 `Steward` 前，必须先满足契约全部条目。

**契约全文见 [`docs/STEWARD_CONTRACT.md`](docs/STEWARD_CONTRACT.md)**，涵盖：

- 契约四原则（manifest + 协议、生命周期归宿主 / 状态归工具、渐进增强、单向依赖）
- `tool.manifest.json` 字段最小集
- 消息信封与二进制帧格式（**长度前缀 + JSON 载荷，单帧上限 1 MiB**）
- 传输通道：**Windows 命名管道**，工具是服务端、宿主是客户端；单实例由传输层天然保证
- 宿主 → 工具命令（`context.update` / `activate` / `deactivate` / `ping` / `shutdown`）
- 工具 → 宿主上报（`ready` / `heartbeat` / `status` / `error` / `log` / `exit`）
- 强制生命周期时序、退出码约定（`0` 正常 / `1` 运行期失败 / `2` 前置不满足 / `3` 版本不兼容 / `4` 单实例冲突）
- 上下文与配置优先级、契约版本管理

## 7. 构建、性能预算与验证

要点摘录，完整规范见 [`docs/BUILD_AND_TEST.md`](docs/BUILD_AND_TEST.md)：

- 产物统一输出到 `build/<preset>/bin/`，禁止散落到源码目录；`build/`、IDE 配置、二进制产物一律忽略。
- 第三方依赖版本必须**锁定**（固定 commit / tag），禁止跟随分支；依赖清单与许可证记录在 `docs/DEPENDENCIES.md`。
- **性能预算必填**，不接受"够快"这类描述：

  | 指标 | 示例基线 |
  | :-- | :-- |
  | 冷启动到 `ready` | ≤ 1500 ms |
  | 空闲常驻内存 | ≤ 300 MB |
  | 交互帧率（如涉及渲染） | ≥ 60 FPS @ 目标分辨率 |
  | 单向消息延迟 | ≤ 10 ms |

  预算超限属于缺陷，不是"后续优化"。

**最小验证要求**（任何改动提交前必须完成）：

1. **干净构建通过**（非增量）：`build.bat windows-ninja-debug`
2. **契约测试通过**：`build.bat windows-ninja-debug test`
3. 若改动涉及工具进程：手动执行一次 `启动 → 就绪 → 收到 shutdown → 退出码 0`，并确认宿主退出后无残留进程。
4. 若改动涉及接口或契约：同步更新对应 `Docs/ARCHITECTURE_DESIGN.md` 与本文档。

> **Agent / 自动化会话注意**：Ninja 预设在该类会话中可能出现"构建完成但进程不退出"（会话环境问题，非工程缺陷，详见 `docs/BUILD.md`）。此时改用 `windows-vs2026-debug` 预设，并**直接调用 `cmake` / `ctest`**，不经 `build.bat`。普通交互式终端不受影响。

**禁止的"验证"**：只看编译通过就宣称完成；只测 `--no-steward` 路径而从未验证协议路径；手工杀进程后不检查孤儿进程。

## 8. 新工具准入评估（立项前必答）

任何候选工具在写入分支前，必须回答以下问题；**任一题不满足即不进入本仓库**。

1. **形态**：它是脚本、CLI 工具，还是常驻/交互应用？（只有后两类才有资格讨论 C++）
2. **瓶颈**：Python 的瓶颈是"内存/CPU/延迟/第三方库缺失"中的哪一个？给出量化证据（延迟目标、数据规模、帧率）。
3. **加速层方案**：能否用"Python 主管 + C++ 扩展模块"解决？若能，则**不新建**独立工具项目，改写 `AtriumPyTools`。
4. **依赖**：所需核心依赖（解码器、渲染器、GUI 框架）在 Python 生态是否确实不可用或不稳定？
5. **预算**：启动时间、内存、帧率、延迟目标是多少？超了会怎样？
6. **宿主关系**：它如何被 `Steward` 管理？准备提供哪些命令与上报？
7. **长期性**：预期维护 3 年以上吗？一年后还会用吗？
8. **落位**：是否与 `AtriumPyTools`、`AtriumSteward`、`Projects/` 已有能力重复？
9. **界面层归属**：界面用原生控件还是 web 渲染（如 WebView2）？若为 web 渲染，必须明确说明**为何仍值得用 C++ 承载**（全库索引、文件 IO、启动延迟、内存、被 `Steward` 托管的原生进程）——因为此时大部分产品价值落在 HTML/JS 侧。本题不需要"通过"，但**必须显式回答**，不允许默认滑过去。

**评估结论只有三种**，不得出现"先做做看"：

| 结论 | 处理 |
| :-- | :-- |
| 脚本即可 | 进 `AtriumPyTools` 脚本层，本仓库不受理 |
| Python 主管 + C++ 扩展 | 改造 `AtriumPyTools` 对应工具，本仓库不受理 |
| 独立 C++ 工具 | 在本仓库建分支，且必须同时产出 §10 级别的量化预算 |

## 10. 活跃需求池（提案区，不是承诺清单）

> 每条需求在立项前必须走 §8 评估。

### 10.1 已立项

| 项 | 内容 |
| :-- | :-- |
| 工具名 | **`Loomery`** |
| 定位 | **Markdown 图文笔记阅读器**：直接读取磁盘上的 Markdown 文件，内嵌 Mermaid 以把笔记里的结构可视化 |
| 形态 | 常驻交互应用（独立可运行） |
| 语言判断 | **C++ 承载核心，渲染面用 web**（暂定 WebView2）。C++ 负责外壳、文件扫描与全库索引、文件 IO、进程生命周期；Markdown 排版与 Mermaid 渲染交给 Chromium |
| 分支 | `tool/loomery` |
| 状态 | 已建最小 Qt 窗口起点；**图渲染栈已实测**；待办：WebView2 宿主成本实测、`Docs/ARCHITECTURE_DESIGN.md` |

#### 10.1.1 核心定位：Markdown 文件为唯一真源

| 维度 | 决策 |
| :-- | :-- |
| **唯一真源** | **磁盘上的 Markdown 文件本身**。它人类可读、可被任意编辑器打开、可被 git 直接版本化 |
| **索引的角色** | 解析产生的块 / 段落结构是**派生物、可随时重建的缓存**，不是真源。删掉索引后从 Markdown 全量重建，语义必须完全一致 |
| **视图** | 文档（阅读为主）/ 图（笔记间的引用关系）；二者是同一份 Markdown 的不同呈现 |
| **Mermaid 的角色** | Markdown 围栏代码块里的内容，交由渲染器画成图。**它是内容的一部分，不是独立存储格式** |
| **规模含义** | 以**文件数与总字节数**衡量，不以"块数"衡量 |

**为什么不用自有块格式**：真源必须是最不易丢失的形态。Markdown 可被任何工具读写、被 git 直接 diff；自有块格式一旦损坏或工具停更，全库内容就成了需要专门工具才能读出的孤岛。且块模型的成本主要在编辑器（拖拽、嵌套、协同、增量持久化），一个以阅读为主、辅以 Mermaid 可视化的工具不需要它。

**保留的能力承诺**：Markdown 里已有的 `[[wiki 链接]]` 与相对路径链接仍要解析成图的边；图视图与全库检索仍是核心能力，它们建立在**重新解析 Markdown** 之上。

#### 10.1.2 量化预算

**A 组：决策输入**

| # | 决策 | 结果 |
| :- | :-- | :-- |
| A1 | 规模 | **全库 10,000 个 Markdown 文件可检索；单篇 ≤ 5,000 行；同屏渲染 ≤ 2,000 个块元素** |
| A2 | 手感优先级 | 启动时间与交互帧率**同等重要**，不做取舍 |
| A3 | 媒体深度 | **MVP 零媒体承载**；未来目标为第 4 档（视频可播放 + PDF 可逐页阅读），接口按此预留 |
| A4 | 独立性 | 脱离 `Steward` 时**完成全部功能**（不加强、不削减）；`Steward` 只做生命周期控制 |

**A1 的量级校准依据**：

| 使用形态 | 文件数 | 总字节量级 |
| :-- | :-- | :-- |
| 个人轻中度 | 300 – 1,000 | 数 MB |
| **本项目目标（个人重度 / 长期全量迁移）** | **10,000** | 数十 MB |
| 团队级 | 50,000+ | 数百 MB |

- < 1,000 文件：可全量载入 + 线性扫描，架构最简单。
- **≈ 10,000 文件（本项目）**：必须有本地全文索引；扫描必须增量（不全量重读）；图视图必须走索引而非全量解析。
- \> 50,000 文件：需要更强的索引层与分页 / 流式；**本项目不追求该档位**。

**关键变量是"单篇的图数量"**：一篇笔记含 1 张图与含 20 张图，开页成本差一个数量级。开页预算必须按"图数量 × 单图成本"核算，不能只看字符数。

**B 组：由 A 组推导的预算（可测量、可验收）**

| 指标 | 基线 | 依据 |
| :-- | :-- | :-- |
| 冷启动到 `ready` | **≤ 1500 ms** | 含索引加载。**不含 WebView2 宿主创建成本——该成本尚未实测，是当前最大风险项** |
| 空闲常驻内存 | **≤ 400 MB** | 10,000 文件不可全量常驻 ⇒ 索引驻留 + 视口内内容。**含 WebView2 的 Chromium 子进程开销（未实测）** |
| 首屏可用 | **≤ 2000 ms** | 先出可读内容，再后台补索引 |
| 滚动 / 缩放帧率 | **≥ 60 FPS** @ 目标分辨率，且在 2,000 块元素同屏条件下 | 单帧 16.7 ms。**未实测**：探针只测到 parse + layout（8.2 ms），**未覆盖 paint / composite** |
| 打开单篇延迟 | **≤ 150 ms** | 阅读手感；受"图数量"约束 |
| 单图渲染（热态） | **≤ 50 ms** | 实测上游 mermaid 为 12.9–29.9 ms，留约一倍余量 |
| 单图渲染（冷态） | **≤ 500 ms** | 含首次加载 `mermaid.min.js`（**3.49 MB**，实测）与主题初始化 |
| 全库搜索（10,000 文件） | **≤ 500 ms**（首次），≤ 100 ms（已建索引） | 超过 1 秒用户会重复触发 |
| 保存 / 增量持久化 | **≤ 50 ms** 落盘、不阻塞输入 | 真源是 Markdown 文件，写入必须原子（临时文件 + 替换） |
| 消息延迟（Steward 通道） | **≤ 10 ms** | 本机管道往返成本极低 |
| **工具退出后残留进程** | **0 个 `msedgewebview2.exe`** | 生命周期契约；WebView2 environment 必须显式释放 |

**A3 的演进触发器**：引入视频连续解码后，帧循环与 GPU 呈现路径进入架构，届时需重写启动时间、常驻内存、单帧预算与依赖面（FFmpeg 体积与许可）。**这些数字现在不填，但必须显式记为待重写，而不是默认沿用。**

**已定案的相邻项**：Markdown 方言（D-14）、C++↔JS 桥（D-16）、MVP 视图边界（D-15）。
**待定案**：Markdown 解析放在显示侧还是索引侧（倾向：显示侧由 `markdown-it` + 插件负责，索引侧由 C++ 只抽取纯文本 / 标题 / 链接 / frontmatter）。

#### 10.1.3 图渲染栈实测（已执行）

比较 `merman` v0.7.0（Rust，无浏览器）与上游 mermaid v11（Chromium），在同一台机器上实测：

| 维度 | `merman-cli`（原生路线） | 上游 `mermaid`（WebView2 路线） |
| :-- | :-- | :-- |
| 单图耗时（含进程启动） | 49 – 75 ms | — |
| 单图耗时（进程内热态） | — | **12.9 – 29.9 ms** |
| 保真度 | 与官方 `mmdc` 逐像素一致（第三方报告） | **即上游本身，100%** |
| SVG 可移植性 | ❌ 节点标签全在 `<foreignObject>`、`<text>` 为 **0** → QtSvg / librsvg / Inkscape 会画出**空框且退出码 0** | ❌ 上游自身也大量使用 `<foreignObject>` |
| 显示路径 | **只能走 PNG 位图**（已实测中文无裁切） | 浏览器内直接渲染：矢量、可缩放、图内文字可选 |
| 依赖面 | 单个 28.8 MB exe；做静态库链接则需引入 **Rust 工具链** | WebView2 运行时（Win10/11 自带）+ `mermaid.min.js` **3.49 MB** |
| Markdown 解析 | 需另配（`md4c` 等） | Chromium **不解析 Markdown**，同样需另配 |

**结论**：两条路线**渲染速度同量级**，差别不在性能，而在**保真度与显示质量**。原生路线被迫降级为 PNG 位图（失去矢量缩放与图内文字选择）；WebView2 路线拿到的是**上游本身**。因此选 WebView2。

**本实测推翻了两个先入为主的判断**：

1. **「web 渲染太慢」不成立。** 某第三方对比报告中 `mmdc` 的 3.0 s **完全是每次新建浏览器的冷启动**，不是渲染耗时；热态渲染只要十几到三十毫秒。
2. **「原生 SVG 可移植」不成立。** 上游 mermaid 自己就大量使用 `<foreignObject>`，这不是某个实现的质量问题，而是 Mermaid 输出的固有形态——**任何"生成 SVG 再交给非浏览器渲染"的方案都会踩这个坑**。

**它还收窄了本工具的语言判断**：既然排版与图渲染都交给 Chromium，C++ 的价值退到**全库索引、文件 IO、启动延迟、内存控制、被 `Steward` 托管的原生进程**。这仍值得用 C++，但"重"应理解为**核心用 C++**，而不是"每一行都用 C++"。

#### 10.1.4 待做的宿主成本实测（阻塞正式定案）

§10.1.3 只测了**渲染器**，没测**宿主**。以下三项必须用一个最小 C++ WebView2 宿主实测，因为它们直接决定生命周期契约是否成立：

| 待测项 | 为什么必须测 | 对应约束 |
| :-- | :-- | :-- |
| 冷启动（创建 environment → 首次导航完成） | WebView2 会拉起 `msedgewebview2.exe` 及子进程，最可能击穿 ≤1500 ms | 启动预算 |
| 常驻内存 | Chromium 多进程通常加 80–250 MB | 内存预算 ≤400 MB |
| **杀进程后是否残留 `msedgewebview2.exe`** | 未正确释放 environment 会留下孤儿进程 | 明确禁止的行为；生命周期契约 |

第三项是选 WebView2 最大的集成风险，也是最容易漏掉的一项。它必须成为 shutdown 流程里的**显式步骤**和**一条测试用例**。
