# 构建、依赖、测试与验证

> **来源**：从 `README.md` §8、§9 拆分而来（2026-09-19 文档瘦身）

## 1. 构建

- 顶层 `CMakeLists.txt` 只负责聚合与全局设置，工具业务逻辑不写在这里。
- 每个工具独立 target，可单独构建：`cmake --build build --target <tool>`。
- 构建产物统一输出到 `build/<preset>/bin/`，禁止散落到源码目录。
- 必须提供一键脚本（`build.bat`）与 `Docs/BUILD.md`。

## 2. 依赖管理

- 第三方依赖版本必须**锁定**（固定 commit / tag），禁止跟随分支。
- 优先复用工作区已有依赖，避免同类库重复引入（例如矩阵库、图像解码库各只允许一套）。
- 依赖清单与许可证必须记录在 `docs/DEPENDENCIES.md`。

## 3. 性能预算（必填，不接受"够快"这类描述）

每个工具在架构文档中必须给出可测量指标：

| 指标 | 示例基线 |
| :-- | :-- |
| 冷启动到 `ready` | ≤ 1500 ms |
| 空闲常驻内存 | ≤ 300 MB |
| 交互帧率（如涉及渲染） | ≥ 60 FPS @ 目标分辨率 |
| 单向消息延迟 | ≤ 10 ms |
| 批量处理吞吐（如涉及解析） | 待工具定义 |

预算超限属于缺陷，不是"后续优化"。

## 4. 产物与仓库卫生

- `build/`、`.cache/`、IDE 配置、任何二进制产物一律忽略。
- 禁止提交 `*.obj` / `*.pdb` / `*.exe` / `*.dll` / `*.lib` / `__pycache__`。
- 每条分支根目录保持只有规范文件，不堆临时文件。

> **框架分支提交纪律**：在 `develop` / `dev/basic` 上提交时禁止 `git add -A`，一律使用显式路径。各分支共用同一工作区，只在工具分支存在的 `.gitignore` 在框架分支上并不存在，未跟踪产物会被误提交。此坑已真实发生过一次（详见 `BRANCH_MODEL.md` §4）。

## 5. 测试分层

| 层级 | 内容 | 是否必需 |
| :-- | :-- | :-- |
| 单元测试 | 纯逻辑、算法、解析、数据模型 | 必需 |
| 契约测试 | manifest 校验、消息信封序列化/反序列化、协议版本拒绝路径 | 必需 |
| 生命周期测试 | 启动到 `ready`、心跳、`shutdown` 优雅退出、退出码正确、单实例冲突 | 必需 |
| 集成测试 | 与 `Steward` 联调，宿主侧挂载/观测/回收 | 必需（接入前） |
| 人工验收 | 视觉输出、交互手感 | 必需（有 UI 时） |

## 6. 最小验证要求（改动前必须核对）

1. 目标工具能独立构建通过（**干净构建，非增量**）：`build.bat windows-ninja-debug`
2. 单元 + 契约测试通过：`build.bat windows-ninja-debug test`
3. 若改动涉及工具进程，手动执行一次 `启动 → 就绪 → 收到 shutdown → 退出码 0`，并确认宿主退出后无残留进程。
4. 若改动涉及接口或契约：同步更新对应 `Docs/ARCHITECTURE_DESIGN.md` 与仓库 `README.md`。

> **Agent / 自动化会话注意**：Ninja 预设在该类会话中可能出现"构建完成但进程不退出"（会话环境问题，非工程缺陷）。此时改用 `windows-vs2026-debug` 预设，并**直接调用 `cmake` / `ctest`**，不经 `build.bat`。普通交互式终端不受影响。

## 7. 禁止的"验证"

- 只看编译通过就宣称完成
- 只测 `--no-steward` 路径，从未验证协议路径
- 手工杀掉进程后不检查是否有孤儿进程
